###### 摘要

由于“上下文膨胀”，大型语言模型 (LLM) 智能体在长期软件工程任务中举步维艰。随着交互历史的增长，计算成本激增，延迟增加，并且由于过去不相关的错误分散注意力，推理能力下降。现有的解决方案通常依赖于智能体无法控制的被动的外部汇总机制。本文提出了 Focus，一种以智能体为中心的架构，其灵感来自于多头绒泡菌（粘菌）的生物探索策略。焦点智能体自主决定何时将关键学习内容整合到持久的“知识”块中，并主动撤回（修剪）原始交互历史记录。使用匹配行业最佳实践的优化脚手架（持久 bash + 字符串替换编辑器），我们使用 Claude Haiku 4.5 评估了 SWE-bench Lite 中的 Focus on N=5 上下文密集型实例。通过鼓励频繁压缩的积极提示，Focus 实现了 22.7% 的词元减少（14.9M →\rightarrow 11.5M 词元），同时保持相同的准确性（两个智能体的 3/5 = 60%）。 Focus 平均每个任务执行 6.0 次自主压缩，单个实例的词元节省高达 57%。我们证明，当给予适当的工具和提示时，有能力的模型可以自主地自我调节其上下文，从而在不牺牲任务性能的情况下为具有成本意识的智能体系统开辟途径。

## 一、简介

“上下文窗口”仍然是自主人工智能智能体的基本瓶颈。虽然最近的模型提供了大量的上下文容量（例如，200k+ 词元），但天真地利用这种容量会带来三个关键挑战：

1. 1.

   成本：在迭代循环中，为每个新的推理步骤重新处理不断增长的历史记录会导致二次成本累积。
2. 2.

   延迟：首次标记的时间随着上下文长度线性降低，使得交互智能体变得迟缓。
3. 3.

   上下文中毒：充满试错日志、失败的测试和冗长的工具输出的长上下文可能会分散模型的注意力，导致“迷失在中间”现象[[1](https://arxiv.org/html/2601.07190#bib.bib1)]。

## 二、相关工作

记忆增强剂。有几种方法可以通过外部存储器解决上下文限制。 MemGPT [[2](https://arxiv.org/html/2601.07190#bib.bib2)] 实现了受操作系统启发的虚拟内存层次结构，允许 LLM 通过显式读/写操作来管理自己的内存。 Voyager [[3](https://arxiv.org/html/2601.07190#bib.bib3)] 使用技能库来存储可重用的代码片段，减少冗余探索。

反思和自我完善。反射[[4](https://arxiv.org/html/2601.07190#bib.bib4)]使智能体能够通过生成存储在情景内存缓冲区中的文本反射来从失败中学习。然而，这是在任务尝试之间进行的，而不是在单个连续轨迹内进行的。 LATS [[5](https://arxiv.org/html/2601.07190#bib.bib5)] 将树搜索与 LLM 推理相结合，但仍然积累完整的轨迹。

上下文压缩。 StreamingLLM [[6](https://arxiv.org/html/2601.07190#bib.bib6)] 通过注意力接收器词元解决无限上下文，但在注意力级别运行，而不是提供智能体级别的内存管理。 LLMLingua [[7](https://arxiv.org/html/2601.07190#bib.bib7)] 压缩提示，但需要单独的压缩模型。

我们的贡献。与之前的工作不同，Focus 实现了轨迹内压缩——智能体在单个任务期间主动修剪自己的历史记录，将学习内容保留在结构化知识块中。这补充而不是取代外部存储器方法。

标准智能体以“仅附加”模式运行：每个想法、工具调用和系统响应都会永久添加到对话历史记录中。这种策略适用于短期任务，但会确保复杂的、开放式的探索失败，因为智能体不可避免地会达到词元限制或因自己之前的失败而感到困惑。

我们建议从被动保留转向主动压缩。受到多头绒泡菌（一种粘液霉菌，它可以探索环境并从死胡同中物理收缩，同时留下化学标记以避免再次探索）的效率启发，我们推出了焦点智能体。该智能体具有内省能力，将其最近的轨迹总结为高级学习，并从其直接上下文中物理删除该轨迹的原始日志。

## 三、方法论

### III-A 粘菌类比

生物系统并不能完美记录用于迷宫导航的每一次肌肉运动；他们保留了学到的地图。同样，探索代码库的智能体不需要记住 10 分钟前 ls -R 输出的 50 行；它只需要记住“配置文件不在 /src 目录中”。

### III-B 架构：焦点循环

Focus 架构向标准 ReAct 智能体循环引入了两个原语：start\_focus 和 complete\_focus. 至关重要的是，智能体对于何时调用这些工具具有完全的自主权 - 没有外部计时器或启发式强制压缩。

1. 1.

   开始焦点：智能体声明它正在调查的内容（例如，“调试数据库连接”）。这标志着对话历史记录中的一个检查点。
2. 2.

   探索：智能体使用标准工具（读取、编辑、运行）来执行工作。
3. 3.

   巩固：当智能体自然完成子任务或遇到死胡同时，它决定调用complete\_focus,，生成以下摘要：

   *•

     尝试了什么？
   *•

     学到了什么（事实、文件路径、错误）？
   *•

     结果如何？
4. 4.

   撤回：系统获取此摘要，将其附加到上下文顶部的持久“知识”块，并删除检查点和当前步骤之间的所有消息。

这将上下文从单调增加的日志转换为“锯齿”模式，其中上下文在探索期间增长，在合并期间崩溃。该模型根据任务结构而不是任意步数控制此循环。

## IV 实验

我们在 SWE-bench Lite 上评估了 Focus 架构，SWE-bench Lite 是软件工程智能体解决实际 GitHub 问题的基准。我们使用 claude-haiku-4-5-20251001 在 N=5 个上下文密集型实例上进行了受控 A/B 比较，并在相同的任务上运行 Baseline 和 Focus 智能体。使用官方 SWE-bench Docker 工具验证了任务是否成功，该工具在隔离的容器中应用补丁并运行原始测试套件。

### IV-A 优化支架

根据 Anthropic 报告的 SWE-bench 最佳实践 [[8](https://arxiv.org/html/2601.07190#bib.bib8)]，我们实现了一个最小的两个工具脚手架：

*•

  持久 Bash：一个有状态的 shell 会话，其中工作目录和环境在调用中持续存在，与开发人员实际使用终端的方式相匹配。
*•

  字符串替换编辑器：通过精确的字符串替换（查看、创建、str\_replace,插入）进行目标文件编辑，避免容易出错的全文件重写。

系统提示指示智能体“尽可能多地使用工具，最好超过100次”并且“在尝试解决问题之前先进行自己的测试”。最大步数设置为 150。

### IV-B 强力按压提示

最初的实验表明，被动焦点提示仅对每个任务产生 1-2 次压缩，并且节省了边际 (6%) 的词元。我们修改了焦点提示，使其更具指导性：

*•

  强制工作流程：“在任何探索之前始终调用start\_focus……在 10-15 次工具调用之后始终调用complete\_focus”
*•

  定期提醒：在 15 次未压缩的工具调用后，系统注入：“提醒：您应该调用 complete\_focus 来压缩您的上下文”
*•

  结构化阶段：明确指导使用 4-6 个重点阶段（探索 →\rightarrow 了解 →\rightarrow 实施 →\rightarrow 验证）

实例：我们选择了五个具有复杂问题陈述的上下文密集型实例：matplotlib\_\_matplotlib-26020,mwaskom\_\_seaborn-2848,pylint-dev\_\_pylint-7080,pytest-dev\_\_pytest-7490,和sympy\_\_sympy-21171.这些实例是根据问题陈述长度（探索复杂性的代表）和历史难度来选择的。

指标：我们跟踪（1）任务成功（补丁是否通过 Docker 中的测试），（2）总词元消耗，（3）压缩事件和消息丢弃，以及（4）每个实例的效率模式。

### IV-D 主要发现

发现 1：在不损失准确性的情况下减少词元。 Focus 实现了 22.7% 的词元总量减少（14.9M →\rightarrow 11.5M），同时保持与 Baseline 相同的准确性（两者均为 3/5 = 60%）。这与我们之前的实验相矛盾，在我们之前的实验中，被动提示显示准确性下降。关键区别：积极的提示强制执行频繁的结构化压缩（每个任务 6.0 与之前的 2.0），可以防止环境被过时的探索日志污染。

发现 2：4/5 实例上的一致节省。将减少的词元集中在 5 个实例中的 4 个上，节省范围从 18% 到 57%。最大的节省发生在需要广泛探索的实例上：matplotlib-26020（-57%，4.0M →\rightarrow 1.7M）、seaborn-2848（-52%，3.4M →\rightarrow 1.6M）和 sympy-21171（-57%，1.6M） →\rightarrow 0.7M)。只有 pylint-7080 显示出使用量增加 (+110%)，其中 Focus 的额外探索（136 次与 63 次 LLM 调用）超过了压缩优势，但两个智能体都通过了测试套件。

发现 3：积极的提示会导致频繁的压缩。通过明确指示压缩每 10-15 次工具调用和定期系统提醒，Focus 平均每个任务压缩 6.0 次（被动提示时为 2.0 次），每个任务丢弃 70.2 条消息。 Claude Haiku 4.5遵循结构化工作流程（探索→\rightarrow压缩→\rightarrow实施→\rightarrow压缩→\rightarrow验证），证明LLM可以被引导积极地自我调节他们的环境。

### IV-E 案例研究：最大节省 (matplotlib-26020)

在 matplotlib-26020 上，两个智能体都通过了测试套件，但 Focus 节省了 57% 的词元（400 万→\rightarrow 170 万）。 Focus 在 71 个 LLM 调用中压缩了 5 倍，而 Baseline 使用了 102 个未压缩的调用。节省的成本来自 Focus 有效地总结了其探索阶段 - 一旦找到相关文件并理解了错误，它就会压缩该上下文并直接进行实施。这展示了理想的情况：探索过程中的频繁压缩可以保留学习内容，同时丢弃冗长的工具输出。

### IV-F 案例研究：当压缩增加开销时 (pylint-7080)

在 pylint-7080 上，Focus 使用的词元比 Baseline 多了 110%（430 万对 210 万），但两个智能体都通过了测试套件。分析显示，Focus 进行了 136 次 LLM 调用，而 Baseline 进行了 63 次调用，其中 8 次压缩丢弃了 80 条消息。这个问题需要大量的反复试验，而 Focus 的压缩有时会丢弃有用的上下文，迫使人们重新探索。这个案例表明压缩并不是普遍有益的：需要迭代细化的任务可能会受到积极的上下文修剪的影响。

### IV-G 分析

积极的提示消除了准确性的权衡：我们早期的被动专注提示实验显示准确性下降（60% vs. 80%）。通过积极提示执行结构化、频繁的压缩，Focus 与基线准确度 (60% = 60%) 相匹配，同时实现了 22.7% 的词元节省。关键见解：压缩的时间和频率比是否压缩更重要。频繁的小压缩（每 10-15 次调用）会保留最近的上下文，同时丢弃陈旧的探索日志，而不频繁的大压缩则可能会丢失关键的实现细节。

探索繁重的任务受益最多：词元节省与探索复杂性相关。需要大量代码库导航的实例（matplotlib、sympy）显示出 50-57% 的节省，因为 Focus 有效地压缩了详细的目录列表、文件内容和失败的尝试。相反，pylint-7080 需要在先前上下文仍然相关的情况下进行迭代细化，从而导致压缩开销超过收益。这表明焦点对于具有不同探索/实施阶段的任务最有价值，而不是需要连续状态积累的任务。

提示策略至关重要：22.7% 的节省需要明确提示“压缩每 10-15 个工具调用”和系统注入提醒。如果没有这些，Claude Haiku 4.5 每个任务仅压缩 2.0 次，节省 6%。这表明当前的法学硕士并不能自然地优化上下文效率——它们需要使压缩成为工作流程的一流部分的脚手架。未来的工作可以探索微调或强化学习以内化压缩启发式。

## 五、讨论

### V-A 压缩的认知税

主动压缩引入了“认知税”——生成摘要所花费的词元以及管理焦点阶段的开销。尽管有这项税收，Focus 在我们的实验中仍实现了 22.7% 的净词元节省。税收在任务生命周期内摊销：每次压缩花费几百个词元，但通过不重新处理陈旧的历史记录可以节省数千美元。对于具有 50 多个工具调用的任务（在 SWE-bench 中很常见），这种摊销强烈有利于压缩。

### V-B 提示与微调

我们的结果需要积极的提示（“压缩每 10-15 个呼叫”，系统提醒）。这就提出了一个问题：法学硕士能否在没有明确指示的情况下学会最佳压缩？当前的模型似乎缺乏内在的成本意识——它们不会自然地优化词元效率。未来的工作可以探索：（1）对压缩注释轨迹进行微调，（2）带有词元成本惩罚的强化学习，或（3）嵌入效率偏好的宪法人工智能方法。

### V-C 限制

1. 1.

   样本大小：我们的评估使用 N=5 个硬实例。虽然足以证明可行性和衡量词元节省，但需要对完整的 SWE-bench Lite 基准 (N=300) 进行验证，以确定哪些任务类型从压缩中获益最多。
2. 2.

   与任务相关的好处：Focus 显示，对于探索繁重的任务可节省 50-57%，但一项迭代细化任务的开销可节省 110%。识别预测压缩效益的任务特征仍然是未来的工作。
3. 3.

   模型概括：我们评估了Claude Haiku 4.5。 GPT-4、Gemini 或开源模型是否表现出类似的压缩行为尚不清楚。激进的提示策略可能需要针对模型进行调整。
4. 4.

   支架依赖性：我们的结果使用优化的双工具支架（bash + str\_replace\_editor). 不同的工具配置可能会显示不同的压缩模式。

## 六、结论

我们已经证明，积极的、模型控制的上下文压缩可以在不牺牲任务准确性的情况下实现显着的词元节省：

1. 1.

   同等准确度下节省 22.7% 的词元：在 5 个上下文密集型 SWE 基准实例上，Focus 将词元总数从 14.9M 减少到 11.5M，同时匹配基线准确度 (3/5 = 60%)。这与假设的准确性-效率权衡相矛盾——通过适当的提示，压缩可以提高效率而不损害性能。
2. 2.

   积极提示是关键：被动提示仅节省 6% 的成本，并且准确性下降。每 10-15 次工具调用进行压缩的明确指令与系统提醒相结合，将每个任务的压缩次数从 2.0 次增加到 6.0 次，节省了 22.7%。当前的法学硕士需要脚手架来优化上下文效率。
3. 3.

   探索繁重的任务受益最多：在 4/5 实例上，词元节省范围为 18% 到 57%，其中需要大量代码库探索的任务节省最多。一项迭代细化任务显示压缩开销超过了收益，这表明 Focus 最适合探索然后实施工作流程。

Focus 架构提供了一种实用的、无基础设施的方法来进行上下文管理，该方法完全在对话中运行。与优化的支架（持久 bash、字符串替换编辑）相结合，它提供了一条通往成本感知智能体系统的途径。随着上下文窗口的增长和智能体任务变得更加复杂，主动压缩对于管理自回归推理中固有的二次成本增长将变得越来越有价值。

未来的工作：(1) 在完整的 SWE 平台 (N=300) 上进行验证，以表征任务类型依赖性； (2) 在没有明确提示的情况下微调或强化学习方法来内化压缩启发式； (3) 结构化压缩，保留特定工件（测试输出、差异）而不是自由文本摘要； （4）跨模型评估（GPT-4，Gemini，开源）以评估泛化能力。
