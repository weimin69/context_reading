## 来源摘要/页面简介

###### 摘要

随着智能体能力的增强，实际限制越来越多地源于受限的上下文窗口而不是模型能力。常见的策略，例如截断、启发式老化和有损摘要，可能会丢弃有用的信息或引入幻觉风险。为了应对这些挑战，我们提出了动态工具输出压缩（DTOC），这是一个基于 LLM 的智能体中可扩展上下文管理的框架，它将上下文更新建模为智能体推理循环中的显式和可逆操作。 DTOC 将完整的工具输出保留在外部存储器中，同时将紧凑的占位符插入活动上下文中，从而在需要时实现选择性重建。我们形式化了 DTOC 机制，将其集成到 ReAct 风格的智能体架构中，并提供面向生产的实现，支持压缩输出的按需恢复。 DeepSWE 上的实验揭示了模型相关的效果：对于响应式模型（Sonnet 4.6，GPT-5.4)，DTOC 减少了输入标记（10.3% 和 12.7%）和智能体步骤（2.4 和 32.3%），同时提高解决率（分别提高 2.5 和 1.5 倍）并降低每个解决任务的成本（每个解决任务的成本降低 3 和 3.5 倍）。对于其他模型，结果更加复杂，GPT-5.5 解决率加倍，成本减半，但对其他模型的解决率没有影响，对成本没有负面影响。消融结果表明可逆性至关重要：仅禁用压缩变体会降低性能，而完整的 DTOC 以大幅降低的上下文成本恢复基线准确性。这些发现表明，显式的、可逆的上下文管理可以提高长程智能体推理的效率，而不会降低任务性能。

## 1 简介

维持长期智能体轨迹的主要挑战是 Transformer 架构中固有的注意力稀缺性 [[20](https://arxiv.org/html/2609.26121#bib.bib1“记忆作为行动：长期智能体任务的自主上下文管理”)，[15](https://arxiv.org/html/2609.26121#bib.bib2“COMPASS：通过不断变化的上下文增强智能体长期推理”)， [12](https://arxiv.org/html/2609.26121#bib.bib3“Longcat-flash-thinking-2601技术报告”)，[1](https://arxiv.org/html/2609.26121#bib.bib4“AI智能体的有效上下文工程”)，[18](https://arxiv.org/html/2609.26121#bib.bib5“Trams：用于远程语言建模的免训练记忆选择”)]。现代大型语言模型 (LLM) 依赖于自注意力，其中每个标记都关注其他每个标记，随着上下文长度 nn 的增长，导致 O​(n2)O(n^{2}) 成对交互[[14](https://arxiv.org/html/2609.26121#bib.bib6“注意力就是你所需要的”)]。随着神经网络的扩展，模型从日益密集的信息“大海捞针”中检索特定“针”的能力会下降，从而降低了其早期显示但任务关键型细节的能力[[8](https://arxiv.org/html/2609.26121#bib.bib9“迷失在中间：语言模型如何使用长上下文”)]。这种限制在经验上表现为“上下文腐烂”，即模型有效推理范围的退化：尽管模型可能支持较大的名义上下文窗口（例如，128k 个标记），但在达到这些限制之前性能通常会下降[[8](https://arxiv.org/html/2609.26121#bib.bib9“迷失在中间：语言模型如何使用长上下文”)]。

这些限制在长期任务中变得尤其严重，例如科学和软件工程工作流程，其中（半）自主智能体必须在许多步骤中集成异构工具输出[[18](https://arxiv.org/html/2609.26121#bib.bib5“Tram：用于远程语言建模的免训练内存选择”），[13](https://arxiv.org/html/2609.26121#bib.bib11“异构多智能体系统的自主任务规划”）， [11](https://arxiv.org/html/2609.26121#bib.bib12“从自主智能体到集成系统，一种新范式：精心策划的分布式智能”)，[10](https://arxiv.org/html/2609.26121#bib.bib31“智能体大语言模型，一项调查”)]。在长轨迹上，提示、工具输出和中间推理的积累使可用上下文饱和，迫使先前的转弯被截断。至关重要的是，最早的消息通常对用户的主要目标、安全约束或关键假设进行编码，导致后续推理继续对原始任务进行逐渐扭曲的表示[[7](https://arxiv.org/html/2609.26121#bib.bib14“GitGoodBench：评估 git 智能体性能的新颖基准”)]。

现有的上下文管理策略在智能体环境中通常被证明是不够的[[20](https://arxiv.org/html/2609.26121#bib.bib1“记忆作为行动：长期智能体任务的自主上下文管理”)]。硬截断，即一旦超出词元预算，旧的段就会被删除，这会导致不可逆的信息丢失，并有效地强制在部分可观察性下进行规划[[2](https://arxiv.org/html/2609.26121#bib.bib15“你知道，对于上下文 - 第二部分：智能体工智能和上下文工程”)，[1](https://arxiv.org/html/2609.26121#bib.bib4“人工智能智能体的有效上下文工程”)]。基于 LLM 的摘要，用于 OpenHands [[16](https://arxiv.org/html/2609.26121#bib.bib26“OpenHands：人工智能软件开发人员作为通才智能体的开放平台”)] 和 Cursor 111<https://www.openhands.dev/>、<https://cursor.com/> 等系统，可以减轻词元增长，但可能会引入抽象错误、幻觉和轨迹延长，从而导致智能体忽略失败信号并重复无效操作 [[7](https://arxiv.org/html/2609.26121#bib.bib14“GitGoodBench：评估 git 智能体性能的新颖基准”)，[5](https://arxiv.org/html/2609.26121#bib.bib16“LLM 支持的智能体的更智能上下文管理”)]。其他有损方法，例如穴居人式压缩222<https://github.com/juliusbrussee/caveman>，面临类似的保真度权衡，而静态观察掩蔽依赖于新近度或大小启发式，无法轻松地从早期推理步骤中恢复相关信息[[7](https://arxiv.org/html/2609.26121#bib.bib14“GitGoodBench：评估 git 智能体性能的新颖基准”)]。

为了解决这些限制，我们引入了动态工具输出压缩（DTOC），这是一个将上下文管理视为显式智能体操作而不是固定的系统级机制的框架。工具输出存储在外部存储器中，并在活动上下文中替换为轻量级引用，允许智能体有选择地隐藏信息，并在以后根据需要恢复信息。因此，DTOC 提供可逆、低风险的上下文压缩，在保持可恢复性的同时减少长程推理期间活动上下文的增长。 <https://github.com/chaturvediabhay24/opencode> 提供了基于 OpenCode 构建并用于主要实验的参考实现。

## 2 相关工作

DTOC 的概念血统可以追溯到 ReAct 框架 [[17](https://arxiv.org/html/2609.26121#bib.bib30“ReAct：在语言模型中协同推理和行动”)]，该框架表明，将显式推理痕迹（“想法”）与动作和观察交错可以比单独推理更稳健地解决问题 [[17](https://arxiv.org/html/2609.26121#bib.bib30“ReAct：协同推理”并在语言模型中行动”）]。 In ReAct, reasoning traces function as a form of inner speech that allows the model to induce, track, and revise action plans while integrating new evidence from the environment.然而，ReAct 是在交互历史相对较短的假设下开发的，并没有明确解决长程轨迹中有限上下文窗口所施加的约束 [[17](https://arxiv.org/html/2609.26121#bib.bib30“ReAct：在语言模型中协同推理和行动”)]。

关于提示压缩的后续工作，特别是 LLMLingua [[6](https://arxiv.org/html/2609.26121#bib.bib18“LLMLingua：​​压缩提示以加速大型语言模型的推理”)]，试图通过使用较小的语言模型来识别和删除基于困惑度的低重要性标记来解决上下文限制。 LLMLingua 报告静态提示的大幅压缩（在某些设置中高达 20 倍），同时在多个基准测试中保持任务性能 [[6](https://arxiv.org/html/2609.26121#bib.bib18“LLMLingua：​​压缩提示以加速大型语言模型的推理”)]。然而，在智能体设置中，基于困惑的压缩可能过于激进：在语言上可预测的标记可能带有较高的特定于任务的语义值，例如执行日志中的唯一标识符、数字参数或错误代码。此外，LLMLingua 本质上是一种有损、单向转换，丢弃无法从压缩提示中完全重建的信息 [[6](https://arxiv.org/html/2609.26121#bib.bib18“LLMLingua：​​压缩提示以加速大型语言模型的推理”)]。相反，DTOC 针对上下文增长的主要来源、工具输出，并通过非破坏性机制控制其可见性，该机制隐藏或显示内容而无需不可逆转的删除。

与此同时，向“上下文工程”的更广泛转变已经成为一门正式学科，涉及向法学硕士提供的信息有效负载的系统优化[[9](https://arxiv.org/html/2609.26121#bib.bib19“大语言模型的上下文工程调查”)，[3](https://arxiv.org/html/2609.26121#bib.bib20“上下文工程2.0：上下文工程的上下文”)，[19](https://arxiv.org/html/2609.26121#bib.bib21 “智能体上下文工程：自我改进语言模型的不断发展的上下文”）]。 Anthropic 的 [[1](https://arxiv.org/html/2609.26121#bib.bib4“AI 智能体的有效上下文工程”)] 在“智能体技能”和“渐进式披露”方面的工作例证了这个方向：智能体维护对外部资源的轻量级引用或句柄，并仅在必要时有选择地加载完整内容，而不是立即将所有信息流式传输到实时上下文中 [[1](https://arxiv.org/html/2609.26121#bib.bib4“AI 的有效上下文工程”智能体”）]。 DTOC 将这一原则从单个文件或查询推广到整个对话状态，将不断演变的交互历史视为动态存储库，智能体可以在推理展开时显式加载或卸载该存储库，从而使智能体能够控制系统启发式。

密切相关的是斯坦福大学的 ACE（智能体上下文工程）框架 [[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文工程：自我改进语言模型的不断演变的上下文”)]，它将上下文概念化为“不断演变的剧本”，通过生成器-反射器-策展人循环积累、完善和组织策略[[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文”工程：自我改进语言模型的不断发展的环境”）]。 ACE 专注于策略表示的高级适应，并展示了长上下文的天真、端到端重写如何导致“上下文崩溃”，其中关键细节在迭代总结期间被无意中删除[[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文工程：自我改进语言模型的不断发展的上下文”)]。 DTOC 是 ACE 的补充：ACE 管理战略剧本的结构和演变，而 DTOC 提供将这些剧本及其依赖的证据跟踪保持在模型的有效注意力范围内所需的低级词元管理和工具输出治理。

## 3 方法论：动态工具输出压缩

本节将动态工具输出压缩 (DTOC) 形式化为结构化、非破坏性上下文管理框架。我们描述了一般机制（第[3.1]节（https://arxiv.org/html/2609.26121#S3.SS1“3.1一般机制概述‣3方法论：动态工具输出压缩‣DTOC：AI智能体中自适应上下文管理的动态工具输出压缩”）），详细介绍了通过显式基于工具的接口的实现（第[3.2]节（https://arxiv.org/html/2609.26121#S3.SS2“3.2通过基于显式工具的控制 ‣ 3 方法论：动态工具输出压缩 ‣ DTOC：AI 智能体中自适应上下文管理的动态工具输出压缩"))，指定底层数据结构（第 [3.3](https://arxiv.org/html/2609.26121#S3.SS3 "3.3 DTOC 数据结构和工具接口 ‣ 3 方法论：动态工具输出压缩 ‣ DTOC: 动态工具输出压缩AI 智能体中的自适应上下文管理”）），最后将 DTOC 置于更广泛的上下文工程环境中（第 [3.4] 节（https://arxiv.org/html/2609.26121#S3.SS4“3.4 上下文工程视角 ‣ 3 方法论：动态工具输出压缩 ‣ DTOC：AI 智能体中自适应上下文管理的动态工具输出压缩”）， [3.5](https://arxiv.org/html/2609.26121#S3.SS5“3.5 与 ACE 和 Playbook Evolution 的关系 ‣ 3 方法论：动态工具输出压缩 ‣ DTOC：用于 AI 智能体中自适应上下文管理的动态工具输出压缩”))。

### 3.1 总体机制概述

DTOC 将上下文管理制定为对工具输出的持久外部存储器的显式智能体级操作。在每个步骤中，智能体都会维护一个最小的活动上下文，其中包括当前用户查询、其推理轨迹以及先前工具输出的精选子集。所有输出都存储在由轻量级标识符索引的结构化存储库中，与“智能体技能”和“渐进式披露”范例保持一致，其中智能体通过句柄而不是原始内容引用资源[[1](https://arxiv.org/html/2609.26121#bib.bib4“AI智能体的有效上下文工程”）]。

DTOC 不是压缩或丢弃信息，而是支持显式检索和卸载操作，允许智能体在词元约束下动态管理上下文。这产生了一个非破坏性的可见性层，其中输出保持持久存储和可恢复，访问由智能体学习的检索策略而不是不可逆的截断控制。因此，DTOC 将瓶颈从存储容量转移到高效访问和检索。

### 3.2 通过显式的基于工具的控制实现

在实践中，DTOC 是通过专用上下文管理工具实现的，该工具将可见性控制公开为显式智能体操作（图 [1](https://arxiv.org/html/2609.26121#S3.F1“图 1 ‣ 3.2 通过基于显式工具的控制实现‣ 3 方法论：动态工具输出压缩 ‣ DTOC：AI 智能体中自适应上下文管理的动态工具输出压缩”））。编排层不依赖于特定于提供商的工具标识符（例如 OpenAI 或 Anthropic 工具 ID），而是在执行时分配自定义标识符，并将每个工具响应包装在包含三个字段的结构化 JSON 对象中： tool\_key, 唯一标识符； tool\_result, 输出内容；以及 estimated\_tokens, 用于上下文预算的近似词元计数。

![参考说明](https://arxiv.org/html/2609.26121v1/x1.png)

图 1：DTOC 的架构。该图显示了可逆的、智能体控制的上下文压缩。最初，所有工具输出都包含在活动上下文中（左）。智能体有选择地禁用不相关的工具输出，以减少词元使用，同时保留其元数据（中）。需要时，可以重新启用之前禁用的输出，而不会丢失信息（右），从而在协调器级别的控制下实现渐进式披露和细粒度的上下文工程。

该智能体与由两个列表参数化的manage\_context工具交互，启用和禁用，每个列表指定一组工具键。调用此工具会更新活动上下文中的输出可见性。禁用的输出被替换为包含工具密钥、时间戳和词元估计的紧凑的纯元数据占位符，而启用的输出则从编排器恢复其完整的tool\_result。该机制将可见性管理与提供者 API 解耦，产生可见、隐藏和可恢复输出的模型无关且统一的表示。

上下文压缩的触发条件通过自然语言工具描述来传达（例如，当上下文接近其极限并且某些输出变得不相关时调用该工具）。此设计将压缩策略委托给智能体而不是固定的启发式方法，这符合 DTOC 以智能体为中心的理念。通过公开每个输出的词元估计，智能体可以在保留有用信息和维护紧凑上下文之间做出明智的权衡。

### 3.3 DTOC数据结构和工具接口

每个 ToolOutput 记录将一个唯一的协调器分配的标识符 (tool\_key) 与外部工具返回的原始内容 (tool\_result), 以及对其词元足迹的启发式估计 (estimated\_tokens), 、调用时间戳以及用于确定内容是否包含在活动上下文中的可见标志相关联。编排器维护一个持久存储𝒮\mathcal{S}，将每个 ToolKey 映射到其相应的记录。

在每个推理步骤中，AssembleContext 过程都会构建活动上下文𝒞\mathcal{C}. 标记为可见的输出被完整合并，而隐藏输出则被仅保留基本元数据（即 ToolKey、估计词元计数、时间戳和隐式隐藏状态指示器）的紧凑占位符所取代。这种设计保留了引用完整性，同时最大限度地减少了词元消耗。

与上下文管理机制的交互是通过 ManageContext 过程进行调解的，该过程接受分别对应于启用和禁用操作的两组 ToolKey 值。该过程更新𝒮\mathcal{S}中的可见性标志，并返回一个状态报告，总结修改的条目以及活动词元计数中产生的变化。这种即时反馈使智能体能够明确地推理上下文广度和词元效率之间的权衡。

界面设计满足三个关键属性。首先，所有压缩操作都是可逆的，因为完整的tool\_result会保留在𝒮\mathcal{S}中，无论其可见性状态如何。其次，智能体可以显式访问元数据，例如词元估计和时间戳，支持知情和自适应上下文选择。第三，该机制与提供者无关，仅依赖于协调器级别的抽象，而不是特定于供应商的工具调用语义。

当编排器包装每个工具输出时，我们使用字符计数启发式 (len(content)/4) 来估计词元计数。向所有模型逐字提供的manage\_context工具说明如下：*“当您感觉上下文限制增加并且某些工具输出的内容不再与当前推理步骤相关时，请使用此工具。可以禁用此类输出以释放上下文空间，并在需要时重新启用它们。”* 没有强加明确的触发阈值；压缩时间完全委托给智能体。无论原始输出大小如何，禁用输出的占位符都会消耗大约 30-50 个词元。当活动上下文接近模型的本机限制时，底层提供程序将应用自己的截断； DTOC 旨在通过主动智能体驱动的压缩来防止达到此阈值，但不会覆盖提供程序级别的行为。

### 3.4 上下文工程视角

我们的方法采用新兴的上下文工程视角，将交互历史和工具输出存储形式化为要主动优化而不是被动积累的信息有效负载[[9](https://arxiv.org/html/2609.26121#bib.bib19“大型语言模型的上下文工程调查”)]。具体来说，DTOC 将上下文工程 [[9](https://arxiv.org/html/2609.26121#bib.bib19“大语言模型的上下文工程综述”)、[3](https://arxiv.org/html/2609.26121#bib.bib20“上下文工程 2.0：上下文工程的上下文”)、[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文工程：自我改进语言模型的不断发展的上下文”)] 操作化为两个水平。首先，它将“渐进式披露”原则从单个资源（例如文件或查询）推广到完整的对话轨迹：过去的消息和工具输出仍然可用于选择性地重新实例化到实时上下文中，但默认情况下不会保留在那里[[1](https://arxiv.org/html/2609.26121#bib.bib4“人工智能智能体的有效上下文工程”）]。这将上下文管理从静态包含转变为动态、需求驱动的访问。其次，DTOC 引入了紧凑的操作词汇表，概念上包括选择、启用、禁用和检索等操作，智能体可以调用​​这些操作来管理其内存占用。这将上下文选择提升为策略的可学习组成部分，而不是固定的系统启发式。

### 3.5 与 ACE 和 Playbook Evolution 的关系

最后，我们将 DTOC 置于智能体上下文工程 (ACE) 框架内 [[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文工程：自我改进语言模型的不断演变的上下文”)]，该框架将上下文视为“不断发展的剧本”，通过生成器-反射器-策展人循环来积累和完善策略。在我们的实验设置中，高级策略适应（例如，切换调试策略或调整研究计划）对应于 ACE 的剧本演化概念，而 DTOC 提供将这些剧本保持在模型有效注意力范围内所需的低级词元和工具输出管理。

这种关注点的分离使我们能够区分战略失败是源于真正的推理错误还是源于上下文病态，例如上下文崩溃，其中关键细节由于重复总结或截断而丢失[[19](https://arxiv.org/html/2609.26121#bib.bib21“智能体上下文工程：自我改进语言模型的不断发展的上下文”)]。通过检测高层决策跟踪和底层 DTOC 操作，我们的方法量化了对工具输出可见性的动态、非破坏性控制在多大程度上提高了长期智能体任务的成功率和样本效率。

## 4 实验设置

我们在 DeepSWE [[4](https://arxiv.org/html/2609.26121#bib.bib34“DeepSWE：测量原始长期工程任务上的前沿编码智能体”)] 的 6 个任务上评估 DTOC，这是真实世界开源软件工程任务的基准，在两种条件下使用 5 个前沿模型：DTOC ON 和 DTOC OFF（表 [1](https://arxiv.org/html/2609.26121#S4.T1“表 1 ‣ 4 实验）设置 ‣ DTOC：用于 AI 智能体中自适应上下文管理的动态工具输出压缩"))。我们使用 DeepSWE [[4](https://arxiv.org/html/2609.26121#bib.bib34“DeepSWE：测量原始长期工程任务上的前沿编码智能体”)]，因为所有任务都需要实现完整的、重要的功能，以产生扩展的智能体轨迹（30-285 个步骤），为现实词元积累下的上下文管理提供自然的压力测试。选择这五个模型是为了跨越与上下文管理直接相关的三个变化轴。首先，提供商多样性：我们包括 Anthropic（Sonnet、Opus）、OpenAI（GPT-5.4、GPT-5.5）和 Google（Gemini），以确保我们的发现不会因单一架构或训练方法而异。其次，上下文窗口大小：所选模型涵盖 128K (GPT-5.4/GPT-5.5)、200K (Sonnet/Opus) 和 1M 词元 (Gemini Flash) 的原生容量，使我们能够测试 DTOC 的优势是否会随着原生上下文容量的增长而减弱。第三，能力层和推理风格：通过将每个提供商的中层和高端模型（Sonnet 与 Opus；GPT-5.4 与 GPT-5.5）配对，我们评估 DTOC 是否有利于模型能力的扩展，而 Gemini Flash 则体现了“大上下文、快速推理”的设计点。总之，这些选择让我们能够隔离提供者、本机上下文大小和模型功能对 DTOC 有效性的影响。

### 4.1 任务和环境

DeepSWE 需要实现能够通过每个项目的完整测试套件的完整功能。这些任务涵盖 Python 项目（Narwhals、FastAPI、sqlite-utils 和 Mashumaro）和 TypeScript 项目（drizzle-orm 和 ts-pattern），范围从单个组合器 (matchEach) 的实现到多文件滚动窗口功能。这些任务会生成长智能体轨迹（30-285 步），并具有大量工具输出积累，使 DeepSWE 成为上下文管理的自然压力测试。

智能体使用 OpenCode 执行，这是一种将推理和工具调用交错的 ReAct 风格的编码智能体。可用的工具集包括文件操作（读取、写入、编辑和apply\_patch),代码智能工具（glob、grep 和 lsp）以及通过 bash 执行 shell。每个模型-条件对都使用相同的智能体配置在所有分配的任务上运行，工具输出封装在包含协调器分配的标识符、原始结果和词元估计的结构化 JSON 信封中。在 DTOC-ON 条件下，智能体还提供了manage\_context 工具，可对先前生成的工具输出进行动态可见性控制（第 [3.2] 节（https://arxiv.org/html/2609.26121#S3.SS2“3.2 通过基于显式工具的控制实现‣ 3 方法：动态工具输出压缩‣ DTOC：用于 AI 智能体中自适应上下文管理的动态工具输出压缩”））。如果所有项目测试都成功通过，任务成功则以二元结果来衡量，否则奖励为 0.00.0。

DTOC’s largest effects appear on medium-difficulty tasks.例如，sqlite-utils 和 mashumaro 仅在特定模型的 DTOC 下解决，这意味着当任务具有挑战性但仍易于处理时，上下文管理可能是区分成功与失败的决定性因素。

### 5.2 Ablation Study

We did carry out a small-scale explorative ablation study on real-world proprietary data and code.为了隔离各个 DTOC 组件的贡献，我们比较了四种配置：无压缩、仅工具跟踪、仅禁用和完全启用+禁用（表 [4](https://arxiv.org/html/2609.26121#S5.T4“表 4 ‣ 5.2 消融研究 ‣ 5 结果 ‣ DTOC：AI 智能体中自适应上下文管理的动态工具输出压缩”)）。

结果表明，在不禁用上下文的情况下实施工具跟踪（“+工具跟踪，不禁用”）会导致性能略有下降，成功率达到 77.8%，同时保持较高的上下文使用率（87K 词元）。文件重新读取的高频率（平均 4.2 次）表明，单独的跟踪会带来巨大的开销，并且需要有效的恢复机制。有趣的是，“仅禁用”配置的性能显着优于未压缩的基线，仅使用 57K 词元即可实现 81.4% 的成功率。这表明积极的上下文修剪可以通过消除“噪声”来提高模型焦点，尽管非零重读平均值（0.1）凸显了不可逆信息丢失的持续风险。 Full DTOC 配置实现了最佳平衡，使用 61K 词元达到了 83.6% 的最高总体成功率。通过集成禁用和动态重新启用功能，该框架完全消除了文件重新读取 (0.0)。这证实了恢复先前压缩的上下文的能力对于实现峰值可靠性至关重要，从而使模型能够超越基线性能，同时保持显着精简的上下文足迹。

## 6 讨论

### 6.1 对结果的反思

DeepSWE 揭示了 DTOC 有效性的模型系列之间的明显差异。 Sonnet 4.6、GPT-5.4 和 GPT-5.5 实现了更高的解决率和更低的成本，而 Opus 4.8 和 Gemini 3.5 Flash 表现出很少或根本没有总体效益。对于 Opus 来说，这种中立性掩盖了互补的任务级效应：DTOC 能够解决 mashumaro，而 DTOC OFF 解决 sqlite-utils，这表明 DTOC 重塑而不是持续扩展模型的能力边界。

三个模型级因素可以解释观察到的变化。首先，本机上下文管理行为显得很重要：已经避免冗余工具交互的模型（例如，GPT-5.4)放大了 DTOC 的优势，而采用许多小推理步骤的模型（例如，Gemini）生成管理开销的速度比 DTOC 更快，可以减少上下文大小。其次，输出的冗长影响有效性； Opus 产生更大的输出（平均 131K），减少了通过压缩可实现的相对节省。第三，遵循指令的忠诚度可能会发挥作用。将通用 manage\_context 提示解释为执行频繁浅层压缩的信号的模型似乎比选择性应用压缩的模型表现更差。这些研究结果表明，DTOC 应适应各个车型系列，或以经过学习的、针对车型的政策为指导。

对于中等难度的任务，例如 sqlite-utils 和 mashumaro，DTOC 通常是区分成功与失败的因素。相比之下，无论压缩如何，诸如 ts-pattern 之类的更简单的任务都能得到一致解决，而诸如 narwhals 和 fastapi 之类的更困难的任务在所有评估条件下仍未得到解决。 Sonnet 在没有 DTOC 的 sqlite-utils 上失败，仅两步后执行就停止了，这说明了上下文饱和如何导致过早的任务放弃。 DTOC 通过在整个长程轨迹中保留可管理的活动上下文来减轻此类故障。

对于压缩响应模型，DTOC 产生了巨大的经济效益，将 Sonnet 4.6 (67%) 和GPT-5.4 (72%) 的每个解决任务的成本降低了约 67-72%。这些收益来自直接词元节省和解决率的提高，这可以在大量成功结果中分摊执行开销。相比之下，在 DTOC 下表现出词元消耗增加的模型（例如 Opus 和 Gemini）会产生相应的成本惩罚，这凸显了针对模型特定部署的需要。

### 6.2 限制

这些发现存在一些局限性。首先，当前的 DeepSWE 任务选择仅包含六个特征请求任务，限制了统计能力和领域覆盖范围；未评估重构和软件架构任务。扩展 DeepSWE 的覆盖范围以包括其他任务类型和编程语言，例如 Go、JavaScript 和 Rust 将提高评估的广度。其次，所有实验都使用一个通用的 manage\_context 提示，这可能与所有模型的指令遵循行为不一致。第三，二元成功指标（定义为是否所有测试都通过）掩盖了有意义的差异 部分的 进步。最后，对每个模型-任务-条件组合仅进行一次试验，从而未测量随机变异的影响。此外，DeepSWE 评估仅比较 DTOC ON 与 OFF，而不直接与其他上下文管理方法进行比较，例如 LLMLingua [[6](https://arxiv.org/html/2609.26121#bib.bib18“LLMLingua：​​压缩提示以加速大型语言模型的推理”)]、提示截断或提取摘要。直接比较并非易事，因为这些方法针对静态提示而不是动态多轮智能体轨迹，但建立相对性能仍然是一个重要方向。 我们注意到 DTOC 是对词元级压缩的补充：在 DTOC 管理其输出间可见性之前，可以在各个工具输出中应用诸如 LLMLingua 之类的方法。

### 6.3 未来的工作

本文应该被视为对该方法的介绍和原理的证明。有几个方向值得进一步研究，以更稳健地研究其在不同环境中的行为，并扩展到新的功能集和方向。首先，更大的基准测试套件、多次独立运行和额外的基线比较将能够对观察到的效果进行统计测试。我们还尝试了其他基准，例如 HotPotQA 以及专有的公司数据和任务，但我们建议首先扩大 DeepSWE 的覆盖范围，以将重点放在上下文管理最重要的长期任务上。其次，在 DeepSWE 上复制消融研究可以进一步隔离不同背景下特定 DTOC 功能的影响。针对专有用例的初步实验表明，完整 DTOC 的性能优于仅关闭上下文的 DTOC 与无 DTOC 的情况。第三，预算感知提示可以公开实时词元计数和上下文预算阈值，帮助智能体做出更明智的压缩决策。此外，在占位符中保留机器生成的摘要的混合压缩机制可以保留有用的预览信息，同时仍然减少上下文大小，这可能有利于喜欢频繁增量压缩的模型。最后，模型自适应压缩策略可以通过相邻的人工智能方法（例如流程挖掘）变得可见，从轨迹中学习或由编排器动态选择，以更好地使压缩行为与特定于模型的推理模式保持一致。

## 7 结论

动态工具输出压缩（DTOC）将上下文管理作为智能体系统中的首要问题，而不是次要的实现细节。通过允许智能体显式控制过去工具输出的可见性，DTOC 将压缩从不可逆的有损操作重新构建为嵌入智能体推理循环中的可逆决策。

根据经验，DTOC 会产生模型依赖性效应。对于压缩响应模型（Sonnet 4.6、GPT-5.4、GPT-5.5)，观察到的解决率有所提高（例如，Sonnet 从 20% 提高到 50%，GPT-5.4 从 33% 提高到 50%），每个解决任务的成本降低了 67-72%。对于Claude Opus 4.8和Gemini 3.5 Flash，解决率保持不变，而词元消耗增加了18-49%，这表明在没有针对模型进行调整的情况下不应部署DTOC。这些发现基于每种条件的单次运行，需要通过重复试验进行验证。

对智能体轨迹的定性分析表明，智能体会自发地采用一系列压缩策略，例如对任务结构和不确定性敏感的先广后深的探索、迭代细化和分块。这种多样性支持了一个中心假设，即压缩决策最好由智能体本身做出，以不断变化的信念和计划为条件，而不是通过固定的外部规则强加。因此，DTOC 在低级上下文窗口机制和高级规划之间架起了一座桥梁，允许压缩作为推理过程的一部分进行原位优化。

总而言之，这些结果表明，上下文工程应被视为智能体设计的核心维度，与规划、工具使用和内存同等重要。 DTOC 提供了一个实用的、与模型无关的框架来执行相同的操作。它实现起来很简单，只需要协调器级别的工具输出跟踪和智能体动作空间中的单个附加工具，与现有的 ReAct 风格的智能体和工具生态系统兼容，并且对于推理风格与选择性、故意压缩相一致的模型有效。基于显式工具的接口，具有编排器分配的标识符和结构化 JSON 信封，确保 DTOC 可以部署在任何 LLM 平台上，而无需依赖于提供商特定的 API 或工具调用机制。展望未来，将 DTOC 与学习压缩策略、分层摘要和多智能体协调机制相结合，可以提供丰富的研究议程。随着模型不断增长和任务变得更加复杂，我们预计类似 DTOC 的机制将成为可扩展、生产级智能体系统的基本组件，这些系统是无损的、智能体驱动的和可逆的。
