# AI 智能体的上下文工程：第 2 部分

十二月 4, 20257 分钟阅读

今年早些时候，Manus 发表了一篇关于 [AI 智能体的上下文工程：构建 Manus 的经验教训](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) 的文章（如果您还没有先读过这篇文章）。然而，这个领域发展很快。在[最近的网络研讨会](https://www.youtube.com/watch?v=6_BcCthVvb8)中，Manus 的 Peak Ji 分享了他们的 智能体 Harness 是如何超越原来的帖子的，特别解决了“上下文退化”和多智能体协调以及动作空间管理的挑战。

本博客深入探讨了 Peak Ji (Manus)、Lance Martin (LangChain) 的经验教训以及最新的行业研究。但在开始之前我们需要一种共同语言。

**上下文工程**是设计一个系统的学科，该系统以正确的格式提供正确的信息和工具，为法学硕士提供完成任务所需的一切。上下文工程包括上下文卸载（将信息移动到外部系统）、上下文缩减（压缩历史记录）、上下文检索（动态添加信息）、上下文隔离（单独的上下文）。

**智能体 Harness** 是包装模型、执行工具调用、管理消息历史循环以及处理上下文工程逻辑的软件。虽然法学硕士提供推理并生成结构化的“工具调用”，但运行框架负责实际的执行和管理。

**上下文退化** 是一种 LLM 的性能随着上下文窗口填满而下降的现象，即使总词元数完全在技术限制内（例如 100 万个词元）。模型以高质量执行的“有效上下文窗口”通常远小于目前大多数模型所宣传的词元限制 < 256k 词元。

**上下文污染**是上下文中存在太多不相关、冗余或冲突的信息，这些信息会分散法学硕士的注意力并降低其推理准确性。

**上下文混乱**是一种失败模式，其中法学硕士无法区分指令、数据和结构标记，或者遇到逻辑上不兼容的指令。当系统指令（全局规则）本身冲突、有太多相似指令或与用户指令冲突时，经常会发生这种情况。

## 1. 上下文压缩和摘要防止上下文腐烂

上下文缩减是防止上下文腐烂的一般概念，我们看到两种不同的方法压缩和总结作为标准出现，优先考虑可逆性而不是压缩。

**上下文压缩（可逆）：** 去除冗余信息，因为它存在于环境中。上下文压缩是可逆的，这意味着如果智能体需要稍后读取代码，它可以使用工具来读取文件。

* **示例：** 如果客服人员编写了 500 行代码文件，则聊天记录不应包含该文件内容。它应该只包含文件路径（例如，`Output saved to /src/main.py`)。

**总结（有损）：** 使用 LLM 总结历史记录，包括工具调用和消息，通常在上下文腐烂阈值处触发，例如128k 词元。在进行总结时，Manus 将最新的工具调用保留为其原始的、完整细节的格式。这可确保模型保持其“节奏”、格式化风格并防止输出质量下降。

* **示例：** 如果上下文 > 128k 标记，则使用 JSON 结构总结最旧的 20 个回合，同时保持最后 3 个回合的原始状态以保持模型的动力。

![上下文缩减策略](https://www.philschmid.de/static/blog/context-engineering-part-2/compact.jpeg)

仅当压缩不再产生足够的空间时，才首选原始 > 压缩 > 汇总。

## 2. 通过沟通来共享上下文，而不是通过共享上下文来沟通

多智能体系统由于上下文污染而失败。如果每个子智能体共享相同的上下文，您将付出巨大的 KV 缓存惩罚，并使模型与不相关的细节混淆。 Manus 将 GoLang 并发性的原则应用到智能体架构中：“通过通信来共享内存，而不是通过共享内存来通信。”

**离散任务：** 对于具有明确输入/输出的任务（例如，“在本文档中搜索 X”），启动一个具有自己上下文的新子智能体，并仅传递特定指令。

**复杂推理：** 仅当子智能体*必须*了解问题的整个轨迹才能发挥作用时（例如，需要查看以前的错误尝试的调试智能体），才共享完整的内存/上下文历史记录。将共享上下文视为要最小化的昂贵依赖项，分叉上下文会破坏缓存。

## 3. 保持模型工具集较小

为法学硕士提供 100 多种工具会导致上下文混乱，模型会产生参数幻觉或调用错误的工具。 Manus 通过分层动作空间解决了这个问题：

**1 级（原子）：** 该模型包含约 20 个核心工具（例如，`file_write`、`browser_navigate`、`bash, search` ...）。这些是稳定且缓存友好的。

**级别 2（沙箱实用程序）：** 指示模型使用 `bash` 工具通过 CLI 调用 ffmpeg，而不是使用`grep` 的特定工具。 Manus 有 `mcp-cli <command>`，将工具定义保留在上下文窗口之外。

**第 3 级（代码/包）：** 对于复杂的逻辑链（例如，“获取城市 -> 获取 ID -> 获取天气”），不要进行 3 个 LLM 往返。提供处理逻辑的库/函数，并让智能体编写动态脚本。

![层次结构](https://www.philschmid.de/static/blog/context-engineering-part-2/hierachy.jpeg)

## 4. 用结构化模式对待“智能体作为工具”

不要过度拟人化你的特工。您不需要相互聊天的智能体（经理、设计师、编码员）的“组织结构图”。相反，将智能体视为工具。

对于主模型来说，“深度研究”或“计划任务”应该只是一个工具调用。主智能体调用`call_planner(goal="...")`，运行框架启动临时子智能体循环并返回结构化结果。这简化了复杂性并保持了运行框架的模块化。

这种“MapReduce”模式允许主智能体将子智能体完全视为确定性代码函数。它可以定义目标、工具和输出模式（例如，特定的 JSON 结构）。这确保返回的数据可以立即使用，无需进一步解析或对话。

## 5. 最佳实践和实施技巧

**不要使用 RAG 来管理工具定义：** 基于语义相似性每步骤动态获取工具定义通常会失败。它创建了一个不断变化的上下文，破坏了 KV 缓存，并将模型与在第 1 回合出现但在第 2 回合消失的“幻觉”工具混淆。

**暂时不要训练自己的模型：** 我们正在经历[痛苦的教训](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)。当下一个前沿模型下降时，您今天构建的运行框架可能会过时。如果你花费数周的时间微调模型或在特定的行动空间上训练强化学习策略，那么你就会将自己锁定在局部最优状态。使用上下文工程作为适应快速改进模型的灵活界面。

**定义“Pre-Rot 阈值”**：如果模型具有 1M 上下文窗口，则性能通常会在 < 256k 左右下降。不要等待 API 抛出错误。在进入“rot”区域之前监视您的词元计数并实施压缩或汇总周期以保持推理质量。

**使用“智能体-as-a-Tool”进行规划：** 在早期版本中，Manus 使用不断重写的 `todo.md` 文件。这浪费了词元（在早期版本的 Manus 中约为 30%）。更好的模式是返回结构化 Plan 对象的特定 Planner 子智能体。该对象仅在需要时才注入上下文，而不是每次都消耗词元。

**安全和手动确认：** 当向智能体提供浏览器或 shell 访问权限时，沙箱隔离是不够的。尝试强制执行词元不离开沙箱的规则，并在继续之前使用循环中断进行手动确认。

**“实习生测试”：** GAIA 等静态基准很快就饱和了，并且与用户满意度不一致。专注于可计算验证的任务。代码编译了吗？命令运行后文件是否存在？子智能体可以验证父智能体的输出吗？尝试在真实环境中使用二元成功/失败指标，而不是主观的法学硕士法官评分。

**拥抱“随机梯度下降”：** Manus 在过去六个月内被重写了五次。浪链对开放深度研究进行了四次重新架构。这是正常的。随着模型变得越来越智能，您的运行框架也会发生变化。如果在模型改进的同时您的运行框架变得越来越复杂，那么您可能会过度设计。

## 结论

也许最大的收获是 Peak 对复杂性的解释。他们已经重写了马努斯五次。在过去六个月中，他们最大的性能提升并不是来自添加复杂的 RAG 管道或奇特的路由逻辑。收益来自于移除东西。

他们删除了复杂的工具定义，以支持一般的 shell 执行。他们删除了“管理智能体”，以支持简单的结构化切换。他们依赖智能体即工具。

随着模型变得越来越强大，我们不应该建造更多的脚手架，我们应该避开模型。上下文工程并不是添加更多上下文。这是关于找到下一步所需的最小有效上下文。
